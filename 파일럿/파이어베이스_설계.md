# 파이어베이스 연동 설계 (구현 완료)

> 2026-09-23 기준 아래 설계대로 구현하고, 실제 프로젝트로 검증을 마쳤다.

프로젝트: `today-homework` · 리전: `asia-northeast3` (서울)
작성: 2026-09-23

---

## 1. 무엇을 쓰고 무엇을 안 쓰나

| 서비스 | 사용 | 비고 |
|---|---|---|
| Cloud Firestore | ✅ | 모든 데이터. 서울 리전 |
| Authentication | ✅ | 이메일/비밀번호 (+ 구글: 선생님용) |
| Cloud Storage | ❌ | **결제 계정(Blaze) 필요** → 쓰지 않음 |
| Cloud Functions | ❌ | Blaze 필요 → 쓰지 않음 |
| Hosting | 나중에 | 배포할 때 |

사진은 Storage 대신 **Firestore에 나눠 담는다**(3절).

---

## 2. 데이터 구조

지금은 `classes` 배열 하나에 학생·숙제·제출물·사진이 전부 중첩돼 있다.
Firestore에서는 이걸 나눈다. 이유는 두 가지다.

- **보안 규칙**을 항목별로 다르게 걸 수 있다
  (제출물은 본인과 담당 선생님만, 반 정보는 반 구성원 전체)
- **필요한 것만 읽는다** — 목록을 열 때 사진까지 딸려오지 않게

```
users/{uid}
  name, role, createdAt, agreedAt,
  isMinor, guardianName, guardianContact,
  classCode            (학생: 속한 반 1개)

classes/{classId}
  name, code, teacherId, teacherName, createdAt

classes/{classId}/students/{uid}
  name, alias, joinedAt

classes/{classId}/homeworks/{hwId}
  title, due, desc, createdAt,
  closed               (선생님이 마감하면 더 제출받지 않음)

classes/{classId}/submissions/{hwId}_{uid}
  hwId, studentUid, studentName, status,
  note, rejectReason, photoCount, lateDays, updatedAt

classes/{classId}/submissions/{...}/photos/{n}
  data            ← base64 사진 1장. 눌렀을 때만 읽는다

events/{eventId}
  title, startDate, endDate, teacherId
```

**비밀번호는 어디에도 저장하지 않는다.** Firebase Authentication이
단방향으로 처리하므로 `pw`, `pwSaved` 필드는 사라진다.
→ 관리자 화면의 "비밀번호 보기" 기능도 함께 사라지고 **초기화만** 남는다.

## 3. 사진을 Firestore에 담는 방법

Storage를 못 쓰므로 Firestore에 담되, 한도 안에서 안전하게 담는다.

| 제약 | 값 |
|---|---|
| 문서 1개 최대 크기 | 1 MiB |
| 무료 저장 용량 | 1 GiB |
| 무료 전송량 | 10 GiB/월 |

- 사진은 1280px JPEG로 줄여 장당 100~300KB
- base64로 담으면 1.33배 → 약 400KB
- **사진 1장 = 문서 1개** 로 나눠 1 MiB 제한을 넘지 않게 한다
- 10명 × 20일 × 1~2장 ≈ 400장 ≈ 120MB → 1 GiB의 12%

### 목록에서는 사진을 읽지 않는다

전송량을 아끼기 위한 규칙이다.

- **목록 화면** — 제목·상태·사진 장수만 읽는다 (문서당 수백 바이트)
- **사진** — 제출물을 눌러 자세히 볼 때만 읽는다

이렇게 하면 선생님이 숙제 현황을 여러 번 열어도 전송량이 거의 들지 않는다.

## 4. 보안 규칙 (요지)

| 대상 | 읽기 | 쓰기 |
|---|---|---|
| `users/{uid}` | 본인 + 담당 선생님 | 본인 |
| `classes/{id}` | 반 구성원 | 담당 선생님 |
| `students` | 반 구성원 | 담당 선생님 |
| `homeworks` | 반 구성원 | 담당 선생님 |
| `submissions` | 본인 + 담당 선생님 | 본인(제출), 선생님(승인·반려) |
| `photos` | 본인 + 담당 선생님 | 본인 |

핵심: **다른 학생의 제출물과 사진은 읽을 수 없다.**
지금은 한 기기 안이라 문제가 없었지만, 서버로 올라가면 규칙이 유일한 방어선이다.

## 5. 코드에서 바뀌는 곳

미리 `Store` 한 곳으로 모아 둔 덕분에 바깥 코드는 거의 그대로 둔다.

| 구간 | 작업 |
|---|---|
| `Store` 내부 | localStorage → Firestore 교체 |
| 로그인/가입 | Firebase Auth로 교체 |
| 렌더 함수 | 동기 → 비동기 처리 (데이터를 기다렸다 그림) |
| 사진 | 제출물에서 분리, 지연 로딩 |
| 마스터 화면 | 비밀번호 보기 제거, 초기화만 유지 |

## 6. 로그인 방식 (확정)

| | 방식 |
|---|---|
| 선생님 | 이름·비밀번호로 가입, 또는 **구글 로그인** |
| 학생 | **선생님이 계정을 발급한다.** 학생 가입 화면은 없앤다 |

구글로 처음 들어오면 학생에게 보여질 이름과 동의를 받아 선생님 계정을
새로 만든다. 이름·비밀번호로 만든 계정과는 서로 다른 계정이다.
구글 계정에는 이 앱의 비밀번호가 없으므로 마이페이지의 '비밀번호 변경'을 감춘다.

### 학생 계정 발급 흐름

1. 선생님이 반 관리에서 학생 이름을 넣는다 (여러 명 한 번에)
2. 앱이 학생별 **아이디와 임시 비밀번호**를 만들어 보여준다
   - 아이디 예: `a3k9-01` (반 코드 기반, 이름과 무관)
   - 선생님이 인쇄하거나 적어서 나눠준다
3. 학생은 가입 없이 **받은 아이디로 로그인만** 한다
4. 첫 로그인 때 비밀번호를 바꾸게 한다

Firebase Auth는 이메일 형식을 요구하므로 내부적으로
`a3k9-01@todayhw.app` 형태로 변환해 쓴다. **학생 화면에는 이메일이라는
말이 나오지 않는다.**

### 이 방식을 고른 이유

- 만 14세 미만도 문제없다 (구글 계정 불필요)
- 아이가 개인정보를 직접 입력하지 않아 **보호자 동의 부담이 줄어든다**
- 같은 이름 문제가 사라진다 (아이디가 고유)
- 학생이 가입 절차를 거치지 않아 설명할 것이 하나 줄어든다

## 7. 코드 구조 — 메모리 거울 방식

렌더 함수 55개를 전부 비동기로 고치는 것은 위험이 크다. 대신 이렇게 한다.

1. Firestore의 변화를 **`onSnapshot`으로 계속 받아** 기존
   `users` / `classes` / `events` 배열에 **같은 모양으로** 채워 넣는다
2. 렌더 함수는 그 배열을 **지금처럼 동기로** 읽는다 → **고칠 필요가 없다**
3. 쓰기만 Firestore로 보낸다 (화면은 즉시 반영, 저장은 뒤따라감)

앱이 인라인 `onclick`을 쓰기 때문에 전체를 모듈로 바꿀 수 없다.
그래서 작은 모듈 스크립트 하나가 Firebase를 불러와 `window.FB`에 얹고,
기존 스크립트는 그것을 가져다 쓴다.

## 8. 구현 후 알게 된 것

설계대로 만들면서 실제로 돌려 보니 걸린 것들. 기록해 둔다.

- **Firestore는 `undefined` 값을 거부한다.** 역할에 따라 빈 필드를 남기면
  저장이 통째로 실패한다. 역할에 맞는 값만 담아야 한다.
- **묶음 저장(batch)은 하나라도 권한이 없으면 전체가 거부된다.**
  학생이 저장할 때 반 정보 수정이 섞여 들어가 제출이 통째로 막혔다.
  역할별로 올릴 것을 나눴다.
- **'서버에서 받은 모습'을 통째로 찍으면 안 된다.** 아직 올리지 않은 로컬
  변경까지 서버 모습으로 오인해, 저장해야 할 것을 건너뛴다. 방금 서버에서
  받은 그 부분만 기록해야 한다.
- **구독은 대상 문서가 생기기 전에 걸면 거부되고 되살아나지 않는다.**
  반 문서를 만들기 전에 건 구독, 첫 제출 전에 건 제출물 구독이 그랬다.
  쓰기가 끝난 뒤에 걸고, 거부되면 몇 번 더 시도하게 했다.
- **사진 권한은 제출물의 주인을 보고 판단한다.** 제출물 문서보다 사진을
  먼저 올리면 주인을 확인할 수 없어 거부된다. 순서를 맞춰야 한다.
- **구글 로그인이 돌아올 주소는 한 곳만 등록돼 있다.** 앱은 `web.app` 주소로
  여는데, 구글에 등록된 주소는 `firebaseapp.com` 쪽뿐이다. `authDomain`을
  앱 주소에 맞춰 바꾸면 구글이 `redirect_uri_mismatch`로 막는다(확인함).
  바꾸려면 구글 클라우드 콘솔의 '승인된 리디렉션 URI'에 먼저 넣어야 한다.
  그전까지는 창을 띄우는 방식(popup)이 기본이고, 창이 막히면 화면을 옮기는
  방식으로 넘어간다.
- **반 명단에 아이디를 넣으면 안 된다.** `classes/{id}/students`는 같은 반
  학생들도 읽을 수 있어서, 거기 로그인 아이디를 두면 서로의 아이디를 알게
  된다. 처음 비밀번호가 모두 같은 동안에는 그대로 남의 계정에 들어갈 수 있다.
  아이디는 학생 계정 문서(`users/{uid}`)에 두고, 선생님이 필요할 때만 읽는다.
- **학생 비밀번호는 앱에서 초기화할 수 없다.** 파이어베이스가 단방향으로
  보관하고, 남의 비밀번호를 바꾸려면 관리자 권한(Blaze 필요)이 있어야 한다.
  그래서 앱은 아이디와 콘솔에서 찾을 주소를 보여 주고, 선생님이 콘솔에서
  직접 바꾸도록 안내한다.
- **내려받는 파일 이름에 한글을 넣으면 안 된다.** 크롬이 이름을 통째로 버리고
  확장자 없는 `download`로 저장한다(확인함). 영문·숫자로만 짓고, 한글 정보는
  파일 안에 담는다.
- **마스터 화면은 더 이상 쓸 수 없다.** 규칙이 본인과 담당 선생님에게만
  자료를 열어 주므로 전체 목록 조회가 불가능하다. 그게 맞는 동작이라
  콘솔에서 관리하라는 안내로 바꿨다.
