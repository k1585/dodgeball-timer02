# 구조 결정

## 결론

**GitHub Pages는 그대로 두고, 이미 쓰는 Firebase에 서버 함수(Cloud Functions)만 더하는 구조**를 권해요.

| 역할 | 선택 | 이유 |
|---|---|---|
| 웹사이트 | GitHub Pages 유지 | 무료, 지금 배포 방식 그대로. 정적 파일이라 안전함 |
| 주문·설정 데이터 | Firebase Realtime Database 유지 | 기존 주문·가격 설정·포트폴리오를 옮길 필요 없음 |
| 첨부 파일 | Firebase Storage로 이전 (단계적) | DB에 base64로 넣는 방식은 용량·비용에 불리 |
| 관리자 인증 | Firebase Auth 유지 + 강한 비밀번호 | 서버가 검증. 코드에 비밀번호 없음 |
| 주문 접수·조회 인증·알림 | Cloud Functions (새로 추가) | 연락처·인증번호·발송 키를 브라우저 밖에서 처리 |
| 문자 | 국내 문자 발송 업체 API (함수에서 호출) | 알림톡은 사업자 등록이 있어야 해서 지금은 문자부터 |
| 결제 | 네이버 스마트스토어 유지 | 요청대로. 사이트 자체 결제는 넣지 않음 |

## 비교한 다른 방법

| 방법 | 장점 | 단점 |
|---|---|---|
| A. Pages + Firebase만 (지금) | 비용 0, 단순 | 인증번호·문자·서버 검증을 할 곳이 없음. 위 감사의 위험 1~4를 막기 어려움 |
| **B. Pages + Firebase + Cloud Functions (권장)** | 데이터 이전 없음. 서버 검증·문자·인증번호 가능 | Firebase 종량제(Blaze) 요금제와 결제 카드 등록이 필요 (무료 사용량이 있음 — 현재 한도는 콘솔에서 확인 필요) |
| C. Pages + Cloudflare Workers 등 별도 서버 | Firebase 요금제를 바꾸지 않아도 됨 | 서버가 두 곳으로 나뉘어 관리가 복잡. Firebase 관리자 키를 외부 서버에 보관해야 함 |
| D. 전체 이전 (Vercel/Supabase 등) | 한곳에서 관리 | 기존 데이터·관리자 화면 전부 다시 만들어야 함. 이번 범위에 비해 과함 |

**확인하지 못한 것:** Firebase·문자 업체의 현재 무료 한도와 단가는 이번 작업에서 확인하지 못했어요. 적용 전에 콘솔과 업체 요금표에서 확인해야 해요. 2024년 말부터 새 프로젝트의 Storage 기본 버킷에 종량제 요금제가 필요하다는 공지가 있었는데, 지금 프로젝트에 해당하는지도 확인이 필요해요.

## 주문 조회 인증 설계

1. 손님이 주문번호 + 휴대폰 번호를 넣어요.
2. 함수 `lookupStart`가 실행돼요.
   - 서버에서 번호와 연락처를 맞춰 봐요.
   - 맞으면 6자리 코드를 만들어 문자로 보내요.
   - 코드는 해시로만 저장해요. 3분 유효, 같은 번호는 1분에 1번만 받을 수 있어요.
   - 틀려도 같은 안내를 보여 줘요. 그래야 남의 주문이 있는지 알 수 없어요.
3. 함수 `lookupVerify`가 코드를 확인해요.
   - 5번 틀리면 15분 동안 잠가요.
   - 맞으면 10분짜리 조회 토큰을 줘요.
4. 토큰으로 공개 정보만 받아요: 상태, 서비스, 품목, 금액, 변경 시각.
   - 연락처·내부 메모·관리자 기록은 주지 않아요.
5. 지금의 `lookup` 공개 노드는 새 방식이 자리 잡으면 지워요(읽기 규칙을 `false`로).

시안의 `FD.otpStart`, `FD.otpVerify`, `FD.publicView`가 이 순서를 브라우저 안에서 흉내 내요. 실제로 옮길 때는 같은 이름의 함수를 서버로 옮기면 돼요.

## 알림 설계

- `FD.notify`처럼 **채널별 어댑터**를 둬요: 사장님 푸시(ntfy) · 고객 문자 · 카카오 알림톡.
- 함수 안에서만 보내요. 키·발신번호는 함수 환경 비밀값에 넣어요.
- 보내는 때: 접수, 견적 확정, 상태 변경.
- 발송 기록에는 받는 번호 뒤 4자리만 남겨요. 인증번호는 남기지 않아요.
- 실패하면 1번 다시 보내요. 그래도 실패하면 관리자 화면에 '실패'로 표시해요. 손님은 사이트 조회로 상태를 볼 수 있어요.
- 수신 동의는 주문 동의 문구에 '진행 안내 문자 수신'을 넣어요. 광고 문자는 보내지 않아요.
- 문자는 발신번호 사전 등록이 필요해요(국내 규정). 개인 번호도 등록할 수 있는지는 업체마다 달라서 확인해야 해요.
- 카카오 알림톡은 사업자 등록 뒤에 추가해요.

## 파일 업로드 안전

- 확장자뿐 아니라 내용도 확인해요.
  - STL: 바이너리 길이 공식이 맞거나 ASCII `facet` 구조가 있어야 해요.
  - 3MF: ZIP 서명과 `3D/3dmodel.model` 파일이 있어야 해요.
  - G-code: 텍스트 명령이어야 해요.
- 첨부 이미지·PDF는 MIME 타입과 앞부분 서명(magic number)을 확인해요.
- 크기 제한: 모델 150MB, 첨부 50MB/파일, 10개까지.
- Storage 규칙: 손님은 쓰기만 하고 읽지 못해요(경로에 서버가 준 업로드 토큰 필요). 읽기는 관리자만 해요.
- G-code는 프린터에서 바로 실행되는 파일이에요. 관리자 화면에서 '다운로드 후 출력 전 확인' 안내를 붙이고, 손님 파일 그대로 출력하지 않는 원칙을 문서로 남겨요.
