# 적용 계획

운영 사이트에는 이번 작업에서 **아무것도 배포하지 않았어요.** 아래는 승인 후 진행할 순서예요. 단계마다 운영 데이터를 지우지 않고, 언제든 이전 `index.html`로 되돌릴 수 있게 해요.

## 0단계 — 지금 바로 할 보안 정리 (반나절, 시안과 무관)

| 할 일 | 방법 | 되돌리기 |
|---|---|---|
| ntfy 알림에서 고객 이름 빼기 | 알림 메시지를 '번호 · 종류 · 금액'으로 | 이전 커밋으로 되돌리기 |
| `lookup` 노드에서 이름 빼기 | 저장 항목에서 `name` 삭제(새 주문부터) | 같음 |
| 관리자 비밀번호 강화 | Firebase 콘솔에서 긴 비밀번호로 변경, PIN은 화면 잠금으로만 | 콘솔에서 다시 변경 |
| 보안규칙 `lookup` 게시 | 저장소의 `firebase-rules.json` 게시 | 이전 규칙 다시 게시 |
| 스마트스토어 상품 링크 등록 | 사이트 설정 값 교체 | 값 되돌리기 |

## 1단계 — 새 주문 화면(C 흐름) 적용 (2~3일)

1. 지금 소스에서 시안 코어의 '질문 목록(데이터) + 화면 그리기' 부분을 옮겨요.
   - 엔진·가격·Firebase 저장 코드는 지금 것을 그대로 써요. 시안 엔진이 운영 코드 그대로라서 금액은 바뀌지 않아요.
2. 색은 지금 브랜드 토큰을 써요.
3. PC에서는 3D 프린팅만 B의 3분할 작업대를 써요.
4. 새 서비스 2종(모델 수정·전문 모델링)은 **사장님이 기본 디자인비를 정한 뒤**에 켜요.
   - 그 전에는 질문 경로에서 숨겨요.
5. 주문 데이터에 필드를 **추가만** 해요: `service`, `quote.kind`, `quote.reasons`.
   - 기존 필드는 지우지 않아요.
   - 관리자 화면은 두 형식을 모두 읽어요.
6. 상태 값은 지금 값을 그대로 두고, 새 값을 더해요.

| 지금 값 | 화면 이름(지금) | 새 흐름에서 |
|---|---|---|
| `new` | 주문 승인 | 그대로 (= 접수) |
| (새) `review` | — | 확인 중 (자동 견적이 안 될 때만) |
| (새) `pay_wait` | — | 결제 안내 |
| `checked` | 요구사항 확인 중 | 그대로 |
| `making` | 제작 중 | 그대로 |
| `done` | 제작 완료 | 그대로 |

7. **베타 경로로 먼저 배포해요**: 저장소의 `beta/index.html` → `https://k1585.github.io/beta/`.
   - 같은 Firebase를 쓰되, 베타 주문에는 `test: true` 표시를 해서 관리자에서 걸러 봐요.
8. 확인이 끝나면 `index.html`을 교체해요.
   - 되돌리기: `git revert` 한 번이면 이전 사이트로 돌아가요. 데이터 구조를 추가만 했으니 이전 사이트도 새 주문을 읽을 수 있어요.

## 2단계 — 서버 함수 (3~5일, 요금제 확인 후)

1. Firebase 종량제 요금제로 전환해요. 사장님 결정이 필요하고, 결제 카드가 필요해요.
2. 함수를 만들어요.
   - `createOrder`: 서버가 다시 견적을 계산하고, 번호를 발급하고, 저장하고, 알림을 보내요.
   - `lookupStart`, `lookupVerify`: 주문 조회 인증번호.
   - `notify`: 알림 어댑터.
3. 문자 업체와 계약하고 발신번호를 등록해요. 키는 함수 비밀값에만 넣어요.
4. 보안규칙을 바꿔요.
   - `orders` 쓰기는 함수만 할 수 있게 해요.
   - `lookup` 읽기를 닫아요.
5. 첨부 파일을 Storage로 옮겨요.
   - 새 주문부터 적용해요.
   - 기존 base64 첨부는 그대로 두고, 관리자 화면은 두 방식을 모두 읽어요.

## 3단계 — 관리자 보강 (1~2일)

- 견적 검토 탭(검토 사유 표시, 확정 금액 입력 → '결제 안내'로 바꾸고 문자 발송)
- 내부 메모, 변경 기록(누가·언제·무엇을)
- 설정: 검토 기준, 스마트스토어 링크, 알림 채널 상태와 발송 기록
- 기존 기능 유지: 화면 문구 편집, 포트폴리오, 첨부 보기, 테스트 주문 필터

## 위험과 대응

| 위험 | 대응 |
|---|---|
| 새 화면에서 금액이 달라짐 | 엔진을 바꾸지 않음. 샘플 7개 파일의 금액 비교를 배포 전 자동 테스트로 실행 (`tests/formats.js`) |
| 기존 주문을 새 관리자가 못 읽음 | 필드 추가만, 읽을 때 두 형식 지원. 베타 기간 동안 운영 관리자 화면 유지 |
| 문자 비용이 늘어남 | 발송 시점 3가지로 제한, 인증번호 1분 1회 제한 |
| 함수 장애로 주문이 안 됨 | 함수 실패 시 지금 방식(직접 저장)으로 대체하는 경로를 1단계 코드에 남겨 둠 |
| 수정·전문 모델링 가격 미정 | 사장님이 정하기 전까지 숨김 |
| 256mm 결정 미정 | 지금은 300mm 거절 + 256mm 초과 검토 전환. 결정 후 설정 값만 변경 |

## 사장님 결정이 필요한 것

1. 추천안(C + B 작업대 + F 내 주문)으로 진행할지
2. 모델 수정·전문 모델링 기본 디자인비, 난이도별 기준 시간
3. 최대 크기 300mm 유지 또는 256mm로 변경
4. Firebase 종량제 전환, 문자 업체 선택(비용 확인 후)
5. 스마트스토어 상품 링크(서비스별 1개 또는 공통 1개)
