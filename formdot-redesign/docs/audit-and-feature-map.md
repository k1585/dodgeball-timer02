# 기존 사이트 감사와 기능 보존 표

조사 대상: 운영 사이트 https://k1585.github.io/ (저장소 `k1585/k1585.github.io`, `index.html` 한 파일)
조사 방법: 실제 배포 파일과 그것을 만드는 빌드 소스(UI·관리자·엔진 스크립트)를 직접 읽고, 같은 계산을 시안에서 다시 실행해 결과를 맞춰 봤어요.

## 1. 현재 구조

| 항목 | 현재 |
|---|---|
| 호스팅 | GitHub Pages (정적 파일 1개, 약 4천 줄) |
| 데이터 | Firebase Realtime Database (`formdot-93d26`, 싱가포르). 노드: `orderNos`, `orders`, `files`(base64 3MB 조각), `site`(문구·포트폴리오·가격 설정), `lookup`(SHA-256 키) |
| 인증 | Firebase Auth 이메일/비밀번호. 관리자 비밀번호 = PIN 4자리 + 고정 접미사 |
| 알림 | ntfy.sh 공개 토픽으로 사장님 폰에 푸시 |
| 결제 | 네이버 스마트스토어 (링크만 연결. 결제 확인은 사람이 함) |
| 문의 | 카카오톡 오픈채팅 링크, 연락처(전화) |
| 빌드 | 소스 조각을 파이썬 스크립트로 합쳐 `index.html` 하나로 만듦 |

## 3. 보안·운영 위험 (시안 작업 중 발견)

이 항목들은 시안과 별개로 운영 사이트에 지금 있는 문제예요. 어느 시안을 고르든 먼저 고치는 걸 권해요.

1. **ntfy 공개 토픽에 고객 이름이 담겨요.** ntfy 토픽 이름은 사이트 코드에 들어 있어서, 코드를 본 사람은 누구나 구독해 새 주문 알림(이름·금액)을 받을 수 있어요. → 알림 내용에서 이름을 빼고 번호와 종류만 보내거나, 서버에서 보내도록 옮겨야 해요.
2. **주문 조회 노드에서 이름이 보여요.** `lookup` 키는 번호(1만 가지)와 연락처로 만들어져서, 누군가의 휴대폰 번호를 알면 번호 1만 개를 다 대입해 그 사람의 주문 이름·금액·상태를 알아낼 수 있어요. → 당장은 `lookup`에서 이름을 빼고, 길게는 인증번호 방식으로 바꿔요.
3. **관리자 비밀번호가 사실상 숫자 4자리예요.** 접미사가 코드에 있어서, 실제로 추측해야 할 경우의 수는 1만 가지예요. Firebase가 시도 횟수를 막아 주긴 하지만 약해요. → Firebase 콘솔에서 관리자 비밀번호를 긴 값으로 바꾸고, PIN 화면은 편의용 잠금으로만 쓰는 걸 권해요. Firebase의 이메일 열거 보호 설정도 켜 주세요.
4. **아무나 주문을 쓸 수 있어요.** 번호만 먼저 잡으면 주문·첨부를 쓸 수 있어서 대량 스팸이 가능해요. → App Check, 또는 서버 함수로 주문을 받는 구조가 필요해요.
5. **첨부 파일을 데이터베이스에 base64로 저장해요.** 용량이 33% 늘고, 데이터베이스 다운로드 요금·용량 한도에 바로 닿아요. → 파일 저장소(Storage)로 옮기는 걸 권해요.
6. **보안규칙 `lookup` 부분이 아직 게시되지 않았어요** (마지막 확인 때 401). 지금 사이트의 주문 조회는 그 전까지 작동하지 않아요.
7. **스마트스토어 링크가 첫 화면 주소예요.** 손님이 어떤 상품으로 결제해야 하는지 알 수 없어요. → 상품 주소를 등록해야 해요.

## 4. 시안 작업 중 세운 가정

- 수정·전문 모델링 기본 디자인비(3,000원 / 9,000원), 난이도별 시간(단순 1시간·보통 2시간·복잡 3.5시간), 기능별 추가 시간은 **제안값**이에요. 관리자 설정에서 바꿀 수 있게 만들었어요.
- 관리자 검토로 넘기는 기준(256mm 초과, 50개 초과, 1kg 초과, 디자인 6시간 초과, 설명 15자 미만, 기타 색상, 해석 불가 파일)도 제안값이에요.
- '결제 확인' 상태는 사장님이 스마트스토어에서 직접 확인한 뒤에만 바꾸는 걸 전제로 했어요. 사이트가 결제를 자동으로 알 방법은 없어요.
- 출력 시간은 지금처럼 손님에게 보이지 않게 했어요. 무게는 보여요.
